# Architecture Decisions - AI Workflow Narsor

This document summarizes the key architectural decisions made for the AI Workflow Narsor project in the MVP phase.

## Decision table

| ID  | Area | Decision | Alternative | Status | Consequences |
|-----|--------|---------|-------------|--------|--------------|
| D1  | Implementation language | **Rust** (with the Axum framework) | Go, TypeScript, Python | ✅ APPROVED | Memory safety, performance, a single binary, easy TUI and API. |
| D2  | Process architecture | **Single Process** (one narsor process) | Microservices | ✅ APPROVED (the process-related part is superseded by D48–D50 in the context of local takeover) | Simpler deployment, no network latency, all components in a single binary. The part about binding execution to the process is now covered by D48 (self-contained execution), D49 (checkpoint as a bundle) and D50 (materialization from a checkpoint). |
| D3  | Persistence | **Filesystem-based storage** (JSON files + folders) | SQLite, PostgreSQL | ✅ APPROVED | Zero DB dependencies, easy backup (copy the folder), structure: `/tasks/{id}/{state,context,events/,artifacts/}`. |
| D4  | Event History | **Hybrid**: Current state (`state.json`) + Append-only log (`events/`) | Full Event Sourcing | ✅ APPROVED | Fast state reads, full history for debugging, the option to migrate to ES in the future. |
| D5  | Workflow DSL | **YAML** + JSON Schema validation | JSON, TOML, custom DSL | ✅ APPROVED | Human readability, easy validation, no need for a custom language parser. |
| D6  | Expressions and conditions | **Static Output Mapping** (fixed output labels) + JSON Contract | Dynamic expressions (CEL, JMESPath) | ✅ APPROVED (the shape of the JSON contract changed by D64; the static label mapping stays) | The action returns `{ output_label, variables, artifacts }`. A `LABEL: next_state` mapping in YAML. No expression engine. **The current response contract is described by D64: `{ choice, reason, variables, artifacts, additional_data, additional_artifacts }`, and the state declares its choices in `choices`.** |

| D9  | Dynamic states | **Static graph**. No modification of the definition during execution. | Dynamic addition of states by AI | ✅ APPROVED | Predictability, easy validation before start. The AI only chooses among existing transitions. |
| D10 | Context modification | **The Engine approves changes**. The agent proposes a patch (`variables` in the result). | Direct write by the agent | ✅ APPROVED | Data consistency safety. The Engine verifies and applies changes to `context.json`. |

| D12 | Artifact Storage | **Filesystem** (`artifacts/` in the task folder) + metadata JSON | S3, Database | ✅ APPROVED | Simple access, easy debugging. The `ArtifactStore` abstraction will allow a future switch to S3. |
| D13 | Workspace Lifecycle | **Created per Execution**, removed on completion (with a `preserve` option). | Shared workspaces | ✅ APPROVED | Isolation of parallel executions. Cleanup after completion (with push verification). |
| D14 | Agent Isolation | **Docker Container** + filesystem isolation | Sandbox, VM, bubblewrap | ✅ APPROVED | The whole thing runs in a container. Isolation through folder structure and FS permissions. |
| D15 | Permissions | **Physical isolation (FS)** + RO/RW mounting | Capabilities rule engine | ✅ APPROVED | All repos side by side in `/code/`. Main repo RW, others RO. Protection against accidental modification. |
| D16 | Secrets | **Environment Variables** / `.env` file (mounted) | Vault, Secret Manager | ✅ APPROVED | Simple management in Docker. Secrets do not end up in logs or the context. |
| D17 | Agent Runtime API | **Analysis before implementation** (inspecting the Claude Code/OpenCode CLI) | Designing "on paper" | ✅ APPROVED | The interface is matched to the real capabilities of the harnesses (batch mode, stream, resume). |
| D18 | Session Resumption | **Priority: `--resume`**. Fallback: New session with a log. | New sessions only | ✅ APPROVED | An attempt to preserve the conversation context. If impossible – continuation based on the history in files. |
| D19 | Agent Output | **Structured JSON** (`{ output_label, data, variables }`) | Text parsing (keyword fallback) | ✅ APPROVED | Enforcing structure on the agent. Fallback only as a last resort. |
| D20 | Invalid Output | **Retry N times** → AgentDecision/HumanDecision → Failure | Immediate failure | ✅ APPROVED (order clarified by D55) | Tolerance for LLM hallucinations. Escalation to a human if the agent does not fix the format. **Current order: re-prompt → conductor → problem** — a format error does not consume `retry_policy`; the engine re-prompts the agent once by resuming the session, then the conductor decides, and finally the operator receives a problem (see D55). |
| D21 | Retry Semantics | **Hierarchical**: Action Retry, Agent Retry, Workflow Retry. | Global retry count | ✅ APPROVED | Precise control over what is repeated (e.g. only the network vs the whole step). |
| D22 | Timeouts | Defined per Action/Wait. After timeout: retry/failure/alternative transition. | Global timeout | ⚠️ IMPLEMENTATION DETAIL | Configuration details in YAML. |
| D23 | Crash recovery | **Status UNKNOWN** + reconciliation based on logs. | Automatic rollback | ✅ APPROVED | Safe resumption. Manual or automatic verification of the state of external systems. |
| D24 | Exactly-once | **At-least-once** + idempotency keys (execution_id/action_id). | Exactly-once | ✅ APPROVED | A realistic approach for external operations (Git, HTTP). Avoiding duplicates via IDs. |
| D25 | Event Delivery | **At-least-once** + deduplication by event_id. | Exactly-once | ✅ APPROVED | Delivery guarantee across restarts. The receiver must handle duplicates. |
| D26 | External Events | **Polling Service** (polling external APIs) | Webhooks / Listening | ✅ APPROVED | The workflow registers a wait (e.g. for a PR). The service asks GitHub and injects an event into the workflow. No webhook server in the MVP. |
| D27 | GitHub Integration | **Minimal**: PR create/merge, CI status. | Full integration | ⚠️ CAN DEFER | Only the operations essential for the MVP. The rest as an extension. |
| D28 | Narsor Assistant | **⚠️ SUPERSEDED BY D55** — the text below is historical. **None in the MVP**. Human-in-the-loop only. | Assistant agent | ⚠️ SUPERSEDED (D55) | Focus on the workflow engine. The assistant as an API client in the future. **The assistant now exists as the conductor — a daemon module, not an API client (D55).** |
| D29 | Assistant Permissions | **⚠️ SUPERSEDED BY D55** — the text below is historical. N/A (no assistant in the MVP). | - | ⚠️ SUPERSEDED (D55) | To be determined when the assistant is added. **The conductor's permissions are defined by D55: read-only, enforced per harness.** |

| D32 | Parallelism in Workflow | **None in the MVP** (sequential). | Parallel branches | ✅ APPROVED | Simpler engine. Parallelism is achieved as separate executions or through sub-agents in the prompt. |

| D35 | Multi-user | **Single-user / Local** in the MVP. | Multi-user with roles | ✅ APPROVED | No auth/authz in the MVP. The file architecture does not block adding users later. |
| D36 | Web UI | **TUI (full-screen) + API** in the MVP. Web later. | Web right away | ✅ APPROVED | Focus on the backend and TUI. The API is shared by all clients. |
| D37 | API Transport | **REST** (operations) + **SSE** (real-time events). | GraphQL, gRPC, WebSocket | ✅ APPROVED | The simplicity of REST, the lightness of SSE for push events. Easy TUI integration. |

| D40 | Repository Change | **No explicit change in the workflow**. A fixed workspace per execution. | Explicit switching in YAML | ✅ APPROVED | If the agent needs another repo, it does so itself (clone) or as a subtask. |

| D42 | Agent Communication | **Indirect** (via Context/Artifacts). | Direct communication | ✅ APPROVED | Agent A writes the result → Engine → Agent A reads the context. |
| D43 | Agent launches Agent | **Not directly**. The agent suggests, the Engine decides and launches. | Delegation by the agent | ✅ APPROVED | Control over the flow stays in the Engine's hands. |
| D44 | Dynamic Workflows (AI) | **None in the MVP**. Workflows are defined up front. | AI generation | ✅ APPROVED | Stability and predictability. The AI can help create the YAML, but does not change it on the fly. |
| D45 | Policy Engine | **Built into the Engine** (simple rules). | Separate component | ⚠️ CAN DEFER | The interface is separated, but the implementation is in core. It can be split out later. |
| D46 | Observability | **Structured Logs + Event History**. | Distributed Tracing, Metrics | ✅ APPROVED | Sufficient for debugging and auditing in the MVP. |
| D47 | Application configuration | **One YAML file found by a cascade** (`--config` → `~/.config/narsor/` → `/etc/narsor/`, the first hit wins, no merging) plus **per-setting resolution** (flag → `NARSOR_*` variable → file → built-in value). An invalid file stops startup; `config show` is the only exception and shows the source of each value. | Merging several files; the data directory as a cascade step; per-project configuration | ✅ APPROVED | A container in Kubernetes: `/etc/narsor/` is the ConfigMap mount point, the home directory may not exist, and the filesystem may be RO (D14, D15). The data directory is an ordinary setting — if it were a cascade step, the file would live in a directory that it itself configures. Secrets stay outside this file (D16). The default harness and agent timeout are defaults, not compulsion: the workflow definition wins (D22). Details: `docs/plans/2026-09-24-001-feat-konfiguracja-aplikacji-plan.md`. |
| D48 | Execution is self-contained | **An execution carries a pinned definition and a pinned base commit**. The `definition.yaml` definition and the base commit are stored per execution, and the definition is preferred over lookup by name in the catalog. | Lookup by name in the catalog, a central definition catalog | ✅ APPROVED | Self-containment: an execution can be resumed or restored without access to the definition catalog. The pinned base allows exact reproduction of the checkpoint Delta (D49). Consequences and rationale: `docs/brainstorms/2026-09-25-rozproszony-narsor-requirements.md`. |
| D49 | Workspace checkpoint as a git bundle | **A workspace checkpoint is a git bundle of the delta relative to the pinned base commit**, stored as a `checkpoint.bundle` file with the working area in `checkpoint.git/`. The alternatives are WIP branches on the product repository (CI noise, permission problems, no support for workflows without git) or a dedicated state repository (dependency on a forge). | WIP branches on the product repository, a dedicated state repository | ✅ APPROVED | The bundle is platform- and host-independent, contains the exact delta of changes (not the whole history), and does not require forking the repository. Safe restoration: takeover always materializes from the checkpoint (D50), regardless of surviving files. Consequences and rationale: `docs/brainstorms/2026-09-25-rozproszony-narsor-requirements.md`. |
| D50 | Materialization only from the checkpoint | **Restoring the workspace (takeover) materializes only from the checkpoint, ignoring surviving directories on the path**. The workspace path is cleaned unconditionally (no recovery of an existing directory). | Recovering a surviving directory, combining existing files with the bundle | ✅ APPROVED | Simplicity: a single source of truth (the checkpoint). Safety: it eliminates a recovery path that would be machine-dependent and could have an inconsistent state. It requires the pinned base (D48) for the restore to be repeatable. Consequences and rationale: `docs/brainstorms/2026-09-25-rozproszony-narsor-requirements.md`. |
| D51 | Agent harness: a stream, not a single dump | **Claude Code and opencode are run in streaming mode** (`claude -p --output-format stream-json --verbose`, measured live on version **2.1.283**; `opencode run --format json`, measured on version **2.0.15**, which already streams NDJSON incrementally without an additional flag) **and every line goes immediately into its own, incremental conversation file for that attempt** (`{state}/executions/{id}/conversations/{action_execution_id}.jsonl`, one line = one narsor envelope with a sequence number, a timestamp, a `narsor`/`stdout`/`stderr` source and the raw content encoded in base64 — preserved byte for byte, even when it is not valid JSON or valid UTF-8). After the attempt closes, the file is compressed to `.jsonl.zst` atomically (temp + fsync + rename); while being written it is an ordinary file appended with whole lines. The file key is `action_execution_id` (D24) — already a fresh UUID for every attempt today, so no new identifier was introduced. | A `read_capped` buffer over the whole of stdout/stderr (as before) + `parse(whole_stdout)` at the end; independent zstd frames written incrementally during the attempt | ✅ APPROVED (the role of the raw line clarified by D60) | The `AgentMessage` event in the log stays truncated as before (the event log is not a content store), but nothing is irrecoverably lost: R9 ("nothing is lost through truncation") is satisfied by this separate record. The harness adapter gets a stateful stream parser instead of `parse(whole)` — it collects only what is needed for the label, the session id and the error (the `result` line for Claude Code; the last `text` part + `sessionID` + `error` for opencode), and all the remaining lines go to the record raw anyway. A missing `result` line in Claude Code (process killed, SIGTERM/SIGKILL, or it simply did not finish in time) is now a harness session error — in streaming mode the raw stdout *is* the whole conversation, so there is no meaningful text to return instead. A new `ActionAttemptFailed` event (`action_execution_id`, `state_id`, `error`, `retry_in_ms`) is emitted right after a failed attempt that will be retried, before the backoff sleep — so an attempt that is going to be retried has a visible status and reason before `ActionRetrying` even occurs; the last, exhausting attempt still emits only `ActionFailed`. Compression only on close (not incrementally during the attempt) was a deliberate choice: an attempt is time-bounded and written by exactly one process, so the only state a reader has to tolerate is a truncated last *line* of an ordinary file — the same problem every text log has — and not a truncated zstd frame. The read cursor is an entry number, not a byte offset, so it survives swapping an ordinary file for a compressed one between refreshes. The new `zstd` dependency is an exception to the previous "no new dependencies" practice — justified by it being the only way to keep the full conversation without unbounded growth of the state files. |
| D52 | Embedded, read-only axum API on loopback with a token | **⚠️ SUPERSEDED BY D53** — the text below describes the state before the local daemon and is historical, not the current contract. **The first step towards D36–D38: an axum server embedded in the TUI process** (not a separate `narsor serve` process — that is M2), listening on `127.0.0.1:0` (a system-assigned port so that several TUI processes on one machine never collide), protected by a random bearer token regenerated for each process, with no persistence and no configuration surface. Three read-only GET endpoints: execution events from a sequence number, the step timeline (`build_timeline`) with an event → position map, and the attempt conversation from an entry number with a byte budget per response. If the bind fails, the TUI does not start and reports the cause — there is no "silently degraded" mode. | The server right away as a separate process (`narsor serve`, Unix socket, caller identity from R29 of the distributed document); TLS on loopback; auth via `axum-extra`'s `Authorization<Bearer>` extractor | ⚠️ SUPERSEDED (D53) | Loopback does not protect against other local users of the same machine — hence the token: the conversation record may contain secrets from tool results (the same sensitivity class as the workspace, D16), so bare `127.0.0.1` without a token would be sufficient. The server is read-only and does not control any execution, so it does not need an `Engine::is_active` check (`docs/plans/2026-09-26-001-*.md`) — two independent readers on one file store are not a race, only two independent writers would be. The event contract in the API is identical to the log — only the transport changes. The response to a missing conversation record (a script step, an attempt without a session, an old log) is a plain `200` with a "no record" variant, not a `404` — the execution and the attempt are real, there is simply nothing to read; `404` is reserved for an execution the store has never heard of. Auth is checked manually in the `middleware::from_fn_with_state` layer, not through the typed `axum-extra` extractor, because the plan requires no body in the rejection, and an extractor rejection renders a short error description. The new `reqwest` dependency (without default features, only `json`) is another exception to "no new dependencies" — justified by `hyper` already being in the tree through `axum`, so the marginal cost is small. **The sentence "the CLI deliberately does not go through this API… the only consumer of the API is the TUI in the same process" is no longer true — see D53.** |
| D53 | The local daemon as the sole owner of `Engine`/`ExecutionStore` | **`narsor daemon` replaces D52's model in its entirety**: one long-lived process (`narsor daemon` / `daemon stop`, graceful SIGTERM) as the sole constructor of `Engine` and the sole opener of `ExecutionStore` for writing; the TUI and every CLI command (including the reading ones — `list`/`show`/`events`/`steps`/`conversation`/`input`) are from now on pure REST(+SSE) clients, discovering or launching the daemon through a discovery file (`{state}/daemon.json`, atomic write, `0600`, PID/address/token/`started_at`) and a spawn lock (`{state}/daemon.lock`, `write_atomic_exclusive`). The API is extended with mutating endpoints (`POST /tasks`, `/executions/:id/resume`, `/input`, `/transition`) and SSE (`/executions/:id/stream`, `/events/stream`), replacing `Engine::subscribe()` as the live-update source. Terminal detach by re-exec of its own binary + `setsid()` in `pre_exec` (not a double fork — safe after the tokio runtime starts, whereas fork is not). | An embedded, ephemeral per-process API (D52, read-only, living and dying with the TUI); `narsor serve` as a separate process right away (deferred from D52, now realized) | ✅ APPROVED | It closes exactly the same gap that D52 deliberately left open: closing the TUI/CLI process silently killed every engine run going in the background. A dispatch model (`202 Accepted` + `execution_id`, work continuing in `tokio::spawn` inside the daemon) instead of holding the HTTP connection open for the whole run — the client's `REQUEST_TIMEOUT` stays unchanged for control calls, only SSE is explicitly excluded from it. `Engine::resume`/`deliver_human_input` split into a synchronous phase ("try to acquire the guard", returns `409` without `.await`) and an asynchronous one (`RunHandle::run_to_completion`, safe for `tokio::spawn`) — the existing single-call methods remain thin wrappers, so `cli::commands`/engine tests do not change their contract. `POST /executions/:id/transition` must itself authoritatively check the legality of the requested transition against the workflow definition (not only `is_active`), because unlike the TUI menu (which never offered an illegal choice) any holder of the bearer token can now ask for it. Full rationale, sequences and implementation decisions: `docs/plans/2026-09-27-001-feat-daemon-lokalny-plan.md`. |
| D54 | Choice of the default agent harness | **The daemon keeps a versioned, atomically written operator override; an agent action chooses: explicit workflow `harness` → daemon override → configuration `agent_harness` → `claude-code`.** (Clarified by D56: the default is read once, at the first attempt of an action, and also applies to in-flight tasks from the next action on.) Built-in workflows do not declare a harness. The choice is available in the TUI (header, `h` key), in the CLI (`narsor harness default get\|set\|reset`) and through authenticated local API endpoints (`/settings/agent-harness`); the snapshot contains a revision, so a client cannot overwrite a newer response with an older one. Codex runs through `codex exec --json`, always with `approval_policy=never`; the default sandbox is `read-only`, and `workspace-write` requires an explicit workflow parameter. | Pinning built-in workflows to Claude Code; a global unversioned file; letting the Codex adapter use `danger-full-access` | ✅ APPROVED | The operator can switch the provider without copying built-in workflows, but a workflow that requires reproducibility can pin it explicitly. A persistent override is validated against registered adapters, and a corrupted or unsupported record is not silently ignored. The local Codex CLI remains the trust boundary for its own profile, authentication and installed skills; Narsor does not install or translate `ce-*`/`om-*` skills. |
| D55 | Conductor: a daemon module working alongside the execution | **The conductor is a daemon module (`src/conductor/`), not a separate REST client** (supersedes D28/D29): it calls the same public `Engine` methods as the API routes (`try_begin_*`), and the operator sees it only through the API and SSE. Sub-points: **(1)** Triggers F1 (no label after re-prompting) and F3 (step failure after `retry_policy` is exhausted) are internal to the engine and durable — a separate process would have to reconstruct them from the SSE stream without replay. **(2)** Its own store `{state}/executions/{id}/conductor/`: `state.json` (atomic, versioned: an in-flight call marker, the queue, per-episode call counters, consumed retries, saved-but-not-applied decisions), `chat.jsonl` (append-only) and `annotations/`. A missing directory in old executions = empty state. All writes go through a single actor per execution; the execution's `state.json` is changed only by the run holding the claim. **(3)** No new execution statuses: a question and a problem are variants of the `InputNeeded` continuation, "conductor working" is a marker plus the events `ConductorStarted{trigger, purpose}` / `ConductorFinished{outcome}`. **(4)** A problem after a step failure: the execution stays `Failed`, the problem is announced by `ProblemRaised`. **(5)** Read-only per harness: a sandbox on claude/codex, an empty `conductor/scratch/` directory on opencode; re-prompting for a label is also read-only. **(6)** The conductor's response is structured (JSON with a decision, label, `data`, `variables`, confidence `high`/`low` — missing = `low` — a rationale, proposals and a message); an unparseable one = failure. **(7)** A format error closes the attempt (`ActionOutputRejected`), a re-prompt is a new attempt (`OutputReprompted{by}`), not `ActionRetrying`. **(8)** A durable record of the agent's last output in the engine metadata. **(9)** An episode key on every trigger, input, proposal and delivery; a stale one = `409`, checked under the same read as the change. **(10)** Claim: F1 runs inline under the run's claim; advisory calls (F3, chat, annotations) do not hold the claim and have their own abort registry, separate from `active_tasks`; every conductor action takes an ordinary claim. **(11)** One call at a time per execution, with a durable queue with two priorities (F1/F3 before chat and annotations), restored after a restart from `state.json` and unanswered chat messages. **(12)** Call replay (R24) only for F1/F3; a failed chat or annotation is an error entry in the chat and nothing more. **(13)** Undoing a decision restores the decision point (a context snapshot saved before application). **(14)** A self-initiated retry after a failure is one attempt per episode, only without side effects conservatively recognized. | A separate REST client process (D28 "assistant as an API client"); new "problem" / "conductor working" statuses; conductor state in the execution metadata | ✅ APPROVED | The daemon's startup hook after `recover()` is the only place of "replay" — acceptable, because a conductor call only reads: a chat message without a reply returns to the queue, and a run interrupted between rejecting the output and re-prompting gets a new pass. D23 reconciliation does not turn a `Running` execution with an F1 marker and no open attempt into `Unknown` (`ConductorInterrupted`); the same marker with an open re-prompt attempt is an ordinary interrupted action, and the marker is cleared. The store lives in the state directory, not in the `tasks/{id}/` working tree, because the latter is cleaned by the workspace sweep after an execution finishes, and the chat history is meant to outlive it (R26). Full rationale and the restart matrix: `docs/plans/2026-09-29-001-feat-dyrygent-i-obsluga-input-needed-plan.md`. |
| D56 | In-flight task harness: a live default, pinned per action | **The harness given when creating a task (the `--harness` request, a profile) is only a fallback, not a pin — a reversal of R42 from the remote backends plan.** An agent action without its own `harness:` reads the installation default once, at the first attempt, and the engine writes it into every subsequent attempt of that action (retries, re-asking for the label, session resumption); a change of the default during an action applies only to the next one. Only an explicit `harness:` in the workflow (in an action or an agent decision, also templated) pins an action. The conductor has no per-task choice: it follows the default from the next call on; `narsor task conductor harness` is gone, and the control plane rejects `SetConductorHarness` (`400 unsupported_command`), the runner settles previously queued ones as rejected. The runner gets the default in every poll/snapshot response (`default_harness`: a name or an unavailability reason computed from the backend's `allows_harness`), a change wakes open long-polls, and the runner reports in the poll query the harness it is on, so the response arrives immediately when it is behind the default; the last applied one is stored in `narsor/harness.json` on the task storage. A harness that the backend does not run or whose binary is not on the runner's `PATH` leaves the task on the current one and is reported as `default_harness_unavailable` (harness, stays, reason) — information, not a problem or a step error. | Pinning the harness to the task at creation (R42, KTD5); a separate conductor harness choice per task; switching mid-action; recording the origin of the task harness (explicit vs default) | ✅ APPROVED | The operator changes the harness because the current one stopped working or is expensive — a change that does not reach work in progress does not solve their problem. The action boundary is the only place where switching does not tear apart the agent's session or retries. Distinguishing "harness from the request" from "harness from the default" would require a new field in `ResolvedEnvironment`; treating both as a fallback does not, and the `environment_identity` hashes stay unchanged. Whoever needs reproducibility declares `harness:` in the workflow (D54). Details: `docs/plans/2026-10-10-001-feat-tui-czytelnosc-globalny-harness-plan.md`. |
| D57 | HOME and harness login: a backend setting, not a task setting | **The local backend by default leaves the task with the daemon's HOME (`local_home: host`), so the harness runs on the same subscription login as from the console — a departure from R17 for the local backend.** `local_home: private` restores a private HOME on the task storage; `local_codex_home` / `local_claude_config_dir` (absolute paths) export `CODEX_HOME` / `CLAUDE_CONFIG_DIR`. Kubernetes has the same choice in `harness_home` in `backend.yaml`, `private` by default. The runner (`--home`, `--codex-home`, `--claude-config-dir`) reads this at every start; none of it ends up in `ResolvedEnvironment` or the environment identity. **Known M1 limitations (D48–D50), deferred to the next iteration:**

* **Takeover does not preserve local commits in the workspace.** Takeover leaves the
  workspace with a detached (`detached`) HEAD pinned to the pinned base commit; any local
  commits or a branch that the execution run itself created inside the workspace (e.g. a workflow
  opening a PR) are not preserved as real commits — they come back as uncommitted changes on a
  detached HEAD, not as a branch with real commit history. The equivalence that this plan
  proves (AE1) holds for workflows whose steps do not commit inside the workspace;
  a workflow that does so is a known M1 gap — to be addressed in the next iteration by
  packing the local branch into the checkpoint and restoring HEAD on takeover.
* **A checkpoint is not tied to a specific transition/event.** Checkpoint capture is
  best-effort and is not pinned to the specific transition or event after which it
  was taken — if the capture fails (logged, not fatal, per the assumption
  of this plan) or the process dies between saving the execution state and taking the checkpoint,
  a later takeover cannot detect that the checkpoint is one or more steps behind the
  execution record — and restores without a warning. Tying each checkpoint to the specific
  transition/event it belongs to, and having takeover warn on a mismatch, is
  deferred to the next iteration.

## MVP strategy summary

1. **Core**: A deterministic state machine engine in Rust (single process).
2. **Persistence**: A flat structure of JSON files and folders (no database).
3. **Workflow**: YAML with a static graph and output mapping (no expressions).
4. **Agent**: Run in Docker, filesystem-isolated (RO/RW), communication through JSON.
5. **Events**: A polling service for external events (no webhooks), SSE for the UI.
6. **UX**: TUI as the main interface, Web planned.
7. **Security**: Isolation through the container and file permissions, secrets through ENV.
