# Hierarchical configuration file, one section per service

## Summary

The configuration file becomes a YAML tree. Its roots are the short names of
the Narsor services (`server`, `web`, `tui`, `cli`, `runner`) plus `global`
for the values more than one service needs. Settings that must be set
together are grouped under the switch that turns them on, and the
configuration layer reports a missing required key. Environment variables
follow the .NET convention: `NARSOR_SERVER__OIDC__ISSUER`. Each binary knows
only `global` and its own section; `config show` collects the check of every
local binary into one answer.

---

## Problem Frame

The file is a flat set of 35 keys (`crates/narsor-shared/src/config/settings.rs`).
An operator cannot see which keys belong to which service, or which keys
must be set together. Many keys already carry a service prefix (`server_*`,
`web_*`, `observer_*`, `local_*`, `tui_*`), which is a tree flattened into
names.

The dependencies are the real cost. Turning on the observer worker requires
its server URL, its secrets directory and a script user (or
`observer_insecure_same_user`). Network mode requires the OIDC issuer and
audience, the TLS termination and the trusted proxies. Nothing in the file
shows these groups: in `deploy/kind/server.yaml` the observer keys sit
between the server keys in one list. The configuration layer does not know
the rules either; the server finds a missing or contradictory key only when
it starts (`crates/narsor-server/src/runtime.rs`).

---

## Requirements

**Tree shape**
- R1. The file is a YAML mapping whose top-level keys are service sections
  (`server`, `web`, `tui`, `cli`, `runner`) and `global`.
- R2. Every setting has exactly one place in the tree: in `global` or in one
  service section. A service section cannot override a value from `global`.
- R3. Settings that belong to one feature are grouped in a nested section
  under that feature (for example `server.oidc`, `server.tls`,
  `server.observer`). Nesting may be deeper than two levels where a group
  needs it.
- R4. A feature that is off by default keeps an explicit switch (`mode`,
  `enabled`) next to its group. The presence of a section alone does not turn
  a feature on.
- R5. An unknown top-level key is ignored by every binary. There is no shared
  list of section names.

**Required and dependent keys**
- R6. Every setting keeps a built-in value, so a file without any section is
  still valid.
- R7. The configuration layer knows the conditional rules: when a switch is
  on, the keys its feature requires must be present, and contradictory keys
  are an error. A missing required key is reported with its full path.
- R8. All violations in a binary's part of the file are reported together,
  as the current parser does, not one at a time.

**Directories**
- R9. `global.root` is the shared base directory. It replaces `--root`'s
  current meaning of "point all three directories at one place" with a
  single setting that the flag overrides.
- R10. The service directories are settings of the service that owns them
  (`server.catalog`, `server.state`, `server.work`). A relative path is
  resolved against `global.root`; an absolute path points outside it. Each
  has a built-in relative default.
- R11. `cli`, `tui` and `web` read `server.state` to find the local daemon.
  This is the only case where a binary reads a key outside `global` and its
  own section.

**Ownership and validation**
- R12. Each binary validates `global` and its own section only: unknown keys,
  value types and the conditional rules of R7. It does not know the schema of
  any other section, with the single exception of R11.
- R13. A binary refuses to start when its own part of the file has an error.
  An error in another service's section never stops it.
- R14. Every binary that reads the file can run a check of its own part
  without starting the service.
- R15. `config show` runs that check in every binary installed next to
  `narsor-cli` and presents the results as one answer: values, their sources
  and errors, per section.

**Environment variables and flags**
- R16. The environment variable of a setting is derived mechanically from its
  path: `NARSOR_` plus the path segments in upper case, joined by `__`
  (`server.oidc.issuer` -> `NARSOR_SERVER__OIDC__ISSUER`).
- R17. The per-setting precedence stays as it is: flag, environment, file,
  built-in value.

**Migration**
- R18. The flat keys and their environment variables are not recognised. An
  old key in a section is reported as an unknown key; an old key at the top
  level is ignored by R5. There is no transition period.
- R19. The file generated by `narsor-cli init` uses the tree, and the comment
  of each setting names the flat key it replaces.
- R20. The deployment manifests (`deploy/`), the packaging scripts (`dist/`)
  and the user and operator documentation are updated to the tree.

## Acceptance Examples

- AE1. **Covers R4, R7.** Given `server.mode: network` and no
  `server.oidc.issuer`, when `narsor-server` starts, it refuses with an error
  that names `server.oidc.issuer`. With `server.mode: trusted` and no `oidc`
  group, it starts.
- AE2. **Covers R7.** Given `server.observer.enabled: true` with both a
  script user and `insecure_same_user: true`, the check reports the
  contradiction before the server starts anything.
- AE3. **Covers R12, R13.** Given an error in the `server` section, when the
  operator runs `narsor-cli` commands that do not start the daemon, they
  work. `narsor-server` refuses to start.
- AE4. **Covers R5.** Given a section written as `sever:`, no binary reports
  it, and the server runs with built-in values. (Accepted risk.)
- AE5. **Covers R10, R11.** Given `global.root: /srv/narsor` and
  `server.state: /var/lib/narsor-state`, the daemon keeps its state in
  `/var/lib/narsor-state`, and the TUI finds the daemon there. With
  `server.state` unset, both use the built-in subdirectory of `/srv/narsor`.
- AE6. **Covers R15.** Given errors in `server` and `web`, `config show`
  prints both sections with their errors marked, next to the rows that are
  valid.
- AE7. **Covers R18.** Given a file with the flat key `server_mode: network`
  at the top level, no binary reports it and the server runs in trusted mode;
  `NARSOR_SERVER_MODE` is ignored the same way.

## Success Criteria

- An operator can read from the file which settings belong to which service
  and which must be set together, without the documentation.
- A missing or contradictory key of a turned-on feature is reported by the
  configuration check with its path, before the service does any work.
- `deploy/kind/server.yaml` rewritten in the tree shows the observer and
  network groups as separate sections.
- Planning does not have to decide the shape of the tree, the env variable
  convention, the precedence, the directory model or the validation scope.

---

## Scope Boundaries

- Separate configuration files or ConfigMaps per service.
- Inheritance or overrides between `global` and service sections.
- A migration tool that rewrites old flat files.
- Remote diagnosis of a server's configuration from a local CLI (a server in
  Kubernetes is checked by running the check inside its container).
- `narsor-observer-worker`, which does not read the file today; it keeps
  receiving its settings from the server. (`narsor-controller local` does
  read the file; planning gave it its own `controller` root.)

---

## Key Decisions

- One place per key, no inheritance: one path gives one value, and
  `config show` never has to explain where an inherited value came from.
- Switch plus grouped section, not "section present = on": it keeps the
  current behaviour readable and a commented-out section unambiguous.
- Hard break without retired-key hints: the old keys are read by nobody; the
  installer's comments are enough help for the few existing installations.
  The current retired-key mechanism (`data_dir`) has no flat key left to
  protect.
- Ignore unknown roots: full separation of knowledge between binaries is
  worth more than catching a misspelt section name.
- Clients read `server.state` instead of a separate rendezvous setting in
  `global`: one controlled exception is simpler than a new concept.
- Diagnostics by asking each binary: no binary needs to know another
  service's schema, so services can evolve their sections independently.

---

## Dependencies / Assumptions

- The binaries sit next to each other (`docs/dev/building-and-testing.md`),
  so `narsor-cli` can find and run them for `config show`.
- Clients use the state directory only for the daemon's rendezvous files
  (`daemon.json`, `daemon.lock`, `daemon.log`, see
  `crates/narsor-api-client/src/api/discovery.rs`).
